## 목적
- `form_input`의 표기를 일관되게 맞춰 후속 단계의 문자열 대조가 성립하게 한다.
- 허용 범위를 3종으로 못박아 AI가 값을 다듬는 것을 막는다.

## 실행 조건
- 호출 주체: intake-agent (workflow Step 02의 **두 번째** 스킬)
- 선행 조건: `input-guard` 판정이 `통과`
- 실행 시점: 일차 분해 이전 1회
- AI 호출: **0회.** 전부 기계 변환이다
- 실행하지 않는 경우: `input-guard`가 `입력오류`를 반환한 경우

## 입력

| 항목 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `form_input` | object(JSON) | 필수 | 사용자 원본 폼 입력 |
| 채움 결과 | object | 필수 | `input-guard`가 반환한 `추후 추가 예정` 맵 |

## 출력

| 항목 | 형식 | 설명 |
|---|---|---|
| 정규화 결과 | object | 데이터 키 6개 구조로 배치된 정규화 값 |
| 변경 이력 | array of object | `{경로, 원본값, 정규화값, 적용규칙}` |
| 유지 항목 | array of object | 규칙을 적용할 수 없어 원본을 유지한 값 `{경로, 값, 사유}` |

## 산출물
- 파일 산출물 없음. 반환값만 intake-agent에 전달한다.
- 전달 대상: intake-agent → `itinerary-decomposition`(다음 스킬)
- 로그: `normalization_validated` 항목의 출력에 `변경이력`과 `유지항목`을 원본으로 기록한다. **변경 이력 누락은 0차 검증 실패다.**

## 허용 규칙 (3종만)

| 규칙 | 대상 | 처리 | 예 |
|---|---|---|---|
| 날짜 | 모든 날짜 값 | `YYYY-MM-DD` 형식으로 통일 | `2026.03.14` → `2026-03-14` |
| 금액 | 모든 금액 값 | **천 단위 콤마를 제거**하고 숫자와 단위만 남긴다 | `120,000원` → `120000원` |
| 공백 | 모든 문자열 값 | 앞뒤 공백 제거 + 내부 연속 공백을 1칸으로 축약 | `제주  올레 ` → `제주 올레` |

### 여행기간 결합 형식

폼은 시작일·종료일을 따로 받지만 확정 데이터표에는 하나의 문자열로 저장한다.

```text
{시작일} ~ {종료일}      예) 2026-03-14 ~ 2026-03-17
```

물결표 앞뒤에 공백 1칸을 둔다. 이 형식이 소개서·상품 페이지 양쪽에서 그대로 쓰이므로 임의 변형하면 검증 실패다.

## 금지 사항

- 지명·시설명의 표기를 바꾸지 않는다. 어순 변경·약칭·영문 변환 모두 금지다.
  - `롯데호텔 제주` → `롯데 제주 호텔` **금지**
  - `성산일출봉` → `성산 일출봉` **금지** (내부 공백 추가는 공백 규칙이 아니다. 공백 규칙은 **축약**만 한다)
- 금액 단위를 바꾸지 않는다. `120000원` → `12만원` 금지, `원` → `KRW` 금지.
- 금액을 계산·합계·환산하지 않는다.
- 오타를 고치지 않는다. 사용자가 `롯대호텔`이라 썼으면 그대로 둔다.
- 문장을 다듬지 않는다. `일정원문`·`상점정보`·`식사정보`는 공백 규칙만 적용한다.
- 값의 타입을 바꾸지 않는다. 모든 값은 문자열로 유지한다(spec §6.1).
- 값을 추가·삭제하지 않는다. `추후 추가 예정` 채움은 `input-guard`가 이미 결정한 것을 반영할 뿐이다.

## 판정 규칙

- 3종 규칙 중 어느 것도 적용할 수 없는 값은 원본을 그대로 두고 `유지항목`에 사유와 함께 기록한다.
- 하나의 값에 여러 규칙이 적용되면 `변경이력`에 규칙별로 각각 1행을 남긴다.
- 정규화 자체는 실패하지 않는다. 정규화 결과가 규칙을 벗어났는지는 **0차 검증**(spec §11.1)이 판정한다.
- **정규화로 인한 표기 차이는 1·2차 검증의 허용 차이다**(spec §11.2). 기준값이 `form_input`이므로 이 명시가 없으면 정상 정규화가 실패로 잡힌다.
