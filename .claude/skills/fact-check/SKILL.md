---
name: fact-check
description: form_input을 기준값으로 소개서(1차) 또는 상품 페이지(2차)의 사실정보가 일치하는지 판정한다. source 맵이 가리키는 경로를 따라 값 단위로 대조하며, 통과/실패와 사유만 반환하고 재시도 여부는 판단하지 않는다.
---

## 목적
- 생성물의 사실정보가 사용자가 실제로 입력한 값과 일치하는지 판정한다.
- AI 임의 생성값·입력 외 고유명사·출처 없는 숫자가 섞였는지 점검한다.

> **2.2에서 바뀐 점**: 기준값이 `confirmed_data` → **`form_input`**으로 교체됐다. `confirmed_data`는 AI가 만든 파생물이므로, 그것을 기준으로 삼으면 정규화·분해 단계의 값 변형을 어느 축도 잡아내지 못했다(spec §11.1). 그 대신 정규화 자체는 **0차 검증**이 판정한다.

## 실행 조건

이 스킬은 **두 번** 호출된다.

| 호출 | Step | 검사 대상 | 로그 |
|---|---|---|---|
| **1차** | Step 04 | `brochure_content` (소개서 8개 섹션) | `validation_1_completed` |
| **2차** | Step 06 | `page_content` (페이지 9개 섹션) | `validation_2_completed` |

- 호출 주체: validator-agent
- AI 호출: **1회.** 각 Step이 쓸 수 있는 AI 호출 1회가 이 스킬에 배정된다(spec §4.2)
- 선행 조건
  - 1차: Step 03이 끝나 `brochure_content`가 DB에 존재함
  - 2차: Step 05가 끝나 `page_content`가 DB에 존재함
- 실행하지 않는 경우
  - **3차 검증(소개서 vs 페이지)** — `consistency-check`가 담당한다. 두 스킬은 같은 요청에서 동시에 실행되지 않는다
  - **0차 검증(정규화 범위)** — 기계 검사 중심이며 Step 02에서 처리한다
  - 편집(Step 08) 이후 — **편집분은 재검증하지 않는다**(spec §10.4)
  - 소개서가 바뀌지 않았는데 페이지만 재생성된 경우 — 1차를 다시 하지 않는다

## 입력

| 항목 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `form_input` | object(JSON) | 필수 | **판정 기준값** |
| `confirmed_data` | object(JSON) | 필수 | 정규화 표기 대조용(허용 차이 판정에 필요) |
| 검사 대상 | object(JSON) | 필수 | `brochure_content`(1차) 또는 `page_content`(2차) |
| 호출 차수 | `1` \| `2` | 필수 | 판정 범위 결정 |
| 치환 결과표 | array of object | 선택 | `intro-content-fill` 출력. 대조 정확도 보조 |
| 이미지 슬롯 목록 | array of object | 2차 필수 | 업로드 시 지정된 슬롯. 이미지 검증용 |

## 출력

| 항목 | 형식 | 설명 |
|---|---|---|
| 판정 | `"pass"` \| `"fail"` | 전체 판정 |
| 검사 항목별 결과 | array of object | `{검증영역, 판정, source경로, 기준값, 발견값}` |
| 불일치 항목 | array of string | 실패한 검증 영역명. 통과면 빈 배열 |
| 상세 사유 | array of string | 항목별 실패 사유 |

```json
{
  "판정": "fail",
  "검사항목별결과": [
    { "검증영역": "행사정보.행사명", "판정": "pass",
      "source경로": "행사정보.행사명", "기준값": "제주 올레 바람 여행", "발견값": "제주 올레 바람 여행" },
    { "검증영역": "숙박.숙소명", "판정": "fail",
      "source경로": "숙박.숙소명", "기준값": "롯데호텔 제주", "발견값": "롯데 제주 호텔" },
    { "검증영역": "가격.성인", "판정": "pass",
      "source경로": "가격.성인", "기준값": "120,000원", "발견값": "120000원" },
    { "검증영역": "항공편.항공사", "판정": "pass",
      "source경로": "항공편.항공사", "기준값": "", "발견값": "추후 추가 예정" }
  ],
  "불일치항목": ["숙박.숙소명"],
  "상세사유": ["숙소명 어순이 변경됨: '롯데호텔 제주' → '롯데 제주 호텔'. 표기 임의 변경은 허용되지 않는다"]
}
```

`가격.성인` 행이 `pass`인 이유: 기준값 `120,000원`과 발견값 `120000원`의 차이는 **정규화 3종에 의한 표기 차이**이므로 허용된다(§허용 차이).

## 산출물
- 파일 산출물 없음. 판정 결과만 validator-agent에 반환한다.
- 전달 대상: validator-agent → 서버 라우트
  - `pass` → 해당 축을 `pass`로 확정하고 다음 단계로 진행
  - `fail` & 재시도 여력 있음 → 카운터 +1, **409** 반환. 클라이언트가 이전 Step부터 재호출
  - `fail` & 재시도 소진 → 해당 축을 `fail`로 확정하고 **200 + 실패 항목** 반환. 생성물은 유지된다
- 로그: 통과·실패 **모두** 기록한다.

## 검사 항목

| 검증 영역 | 확인 내용 | 1차 | 2차 |
|---|---|:---:|:---:|
| 값 일치 | `source` 경로의 값이 `form_input` 대응 값과 일치 | ● | ● |
| 치환 | 미치환 토큰(`{{...}}`)·조사 파이프 기호 0건, 오치환 0건 | ● | ● |
| `source` 존재 | 모든 사실정보 필드에 `source`가 있음 | ● | ● |
| 출처 없는 수치 | `form_input`에 출처 없는 아라비아 숫자 0건 | ● | ● |
| 입력 외 고유명사 | 입력에 없는 지명·시설·경유지·관광지·부대시설 0건 | ● | ● |
| 일정 일치 | 일차 수가 여행기간과 정확히 일치 | ● | ● |
| 일차 서술 범위 | 각 일차 서술이 `원문근거` 범위 내 | ● | ● |
| 선택 항목 | 미입력 항목이 `추후 추가 예정`으로 표기, 섹션 삭제 0건 | ● | ● |
| 섹션 구성 | 8개(1차) / 9개(2차) 순서 고정, 임의 추가 0건 | ● | ● |
| 이미지 | `image_slot` 값이 업로드 시 지정 슬롯과 동일, `alt` 존재 | | ● |
| 헤드라인 길이 | `hero.headline` 40자 이내, 값 잘라내기 0건 | | ● |
| 테마 영향 | 테마로 인한 섹션·문구·사실정보 변경 0건 | | ● |
| `apply` 일치 | `apply` 내부 가격·행사 정보가 `price`·`hero`와 일치 | | ● |

## 허용 차이

| 허용 | 예 |
|---|---|
| 앞뒤 공백, 내부 연속 공백 축약 | `제주  올레` ↔ `제주 올레` |
| HTML 이스케이프 | `&` ↔ `&amp;` |
| **정규화 3종에 의한 표기 차이** | `120,000원` ↔ `120000원`, `2026.03.14` ↔ `2026-03-14` |
| 값을 둘러싼 서술 문장의 분량·어순·문장 수 | 소개서 압축 ↔ 페이지 확장 |

## 실패로 판정하는 차이

| 실패 | 예 |
|---|---|
| 값의 어순 변경 | `롯데호텔 제주` → `롯데 제주 호텔` |
| 약칭·영문 변환 | `성산일출봉` → `성산봉`, `제주` → `Jeju` |
| 값의 날짜 재표기 | `2026-03-14 ~ 2026-03-17` → `3월 14일~17일` |
| 값의 요약·부분 삭제 | `조식 3회, 중식 2회` → `조식·중식 포함` |
| 값의 단위 변경 | `120000원` → `12만원` |
| 실재하지 않는 명칭 생성 | 입력에 없는 호텔명·관광지 추가 |
| 출처 없는 숫자 | `약 2시간 소요`, `총 5개 코스` |
| `추후 추가 예정` 변형 | `미정`, `추후 안내`, 빈칸 |

## 판정 규칙

- `source` 경로를 따라가 값 단위로 대조한다. 문장 전체를 문자열 비교하지 않는다.
- **`source`가 없는 사실정보 필드는 그 자체로 `fail`**이다. 검증 불가이기 때문이다.
- 값이 `추후 추가 예정`·`해당 없음`인 항목은 그 문자열이 그대로 표기됐으면 `pass`다.
- 하나라도 `fail`이면 전체 판정은 `fail`이다.
- 실패 항목은 **전부** 반환한다. 첫 실패에서 멈추지 않는다 — 기획자가 실패 항목 전체를 열람해야 하기 때문이다(spec §11.5).
- **재시도 여부를 판단하지 않는다.** 통과/실패와 사유만 반환한다. 재시도 판단은 클라이언트가 응답 코드로 한다.
- 이미지-텍스트 **내용** 정합성(사진 속 장소가 여행지와 같은지)은 판정 대상이 아니다. 기획자 책임이다(spec §7.3).

## 프롬프트

⚠️ **아래 코드 블록이 실행되는 시스템 프롬프트다.** 코드젠(`npm run build:harness`)이 이 블록의
내용을 바이트 그대로 뽑아 `lib/ai`에 넘긴다. 위의 산문은 사람이 읽는 명세이고, 실행되는 것은 이 블록이다.

**1차·2차가 같은 프롬프트를 쓴다.** 차이는 매니페스트의 `args`가 넘기는 대조 대상뿐이다
(`target: brochure` / `target: page`). 프롬프트가 한 벌이므로 두 축의 판정 기준이 어긋날 수 없다.

⚠️ 산문에 없는 허용 차이 3종이 프롬프트에 있다 — **결합 1종**(여행기간 2필드 → 1문자열),
**채움 1종**(빈 선택 항목 → `추후 추가 예정`), **분해 1종**(`행사정보.일정`이 `form_input`에 없는 것).
이 3개를 지우면 **정상 동작이 전부 실패로 잡힌다.** `form_input`이 기준값이기 때문에 반드시 명시해야 한다.

```text
너는 생성물의 사실정보가 사용자 원본 입력과 일치하는지 판정한다.

기준값은 항상 **form_input**이다. 생성물이 기준값과 다르면 실패다.

허용 차이 (실패가 아니다):
- 앞뒤 공백, 내부 연속 공백 축약
- HTML 이스케이프
- 정규화 3종: 천 단위 콤마 제거(120,000원 → 120000원), 날짜 형식 통일(2026.03.14 → 2026-03-14)
- **결합 1종: 여행기간_시작과 여행기간_종료를 «{시작} ~ {종료}»로 합친 것.**
  form_input에는 여행기간이라는 필드가 없고 시작·종료 2개로 나뉘어 있다. 이는 정상이며 실패가 아니다.
- **채움 1종: form_input이 빈 문자열(«») 인 선택 항목이 «추후 추가 예정»으로 채워진 것.**
  채움은 확정 데이터표에서만 일어나므로 form_input 쪽에는 빈 값이 남아 있는 것이 정상이다.
  기준값이 비어 있고 발견값이 «추후 추가 예정»이면 **통과다.**
  그 역 — form_input에 실제 값이 있는데 생성물이 «추후 추가 예정»이면 실패다.
- **분해 1종: «행사정보.일정»은 «행사정보.일정원문»을 일차 단위로 분해한 결과다.**
  form_input에 «행사정보.일정» 키가 **없는 것이 정상**이며, source 경로가 form_input에 없다는
  이유만으로 실패 판정하지 않는다. 이 영역에서 볼 것은 일차 수와, 일차별 장소·활동·식사가
  일정원문에 등장하는가뿐이다. 원문근거 대조는 이 검증의 몫이 아니다.
- 값을 둘러싼 서술 문장의 분량·어순·문장 수 차이

실패로 판정하는 차이:
- 값의 어순 변경 (롯데호텔 제주 → 롯데 제주 호텔)
- 약칭·영문 변환, 날짜 재표기, 요약·부분 삭제, 단위 변경
- 입력에 없는 지명·시설·경유지·관광지 등장
- 출처 없는 숫자. 단 일차 번호와 여행기간에서 파생된 수(일수, 일수-1)는 정상이다
- 「추후 추가 예정」이 다른 문구로 바뀌거나 빈칸이 된 경우
- source가 없는 사실정보 필드

실패 항목은 **전부** 반환한다. 첫 실패에서 멈추지 않는다.
재시도 여부는 판단하지 않는다. 통과/실패와 사유만 반환한다.
```

## user 지시문 · 소개서

⚠️ **아래 펜스가 1차 검증의 user 메시지에 그대로 실린다.** 기준값(`form_input`)·참고
(`confirmed_data`)·검사 대상(`brochure_content`)은 `lib/harness/ai-skills.ts`가 조립하고,
**지시 문장은 여기가 유일한 출처다**(규약 R4).

둘째 줄이 핵심이다 — `source`가 `"generated"`인 필드는 대조할 기준값이 없으므로
「값이 같은가」가 아니라 「**입력에 없는 요소가 섞였는가**」만 본다. 이 구분이 없으면
AI가 생성 필드를 값 불일치로 반려한다.

```text
각 섹션의 source가 가리키는 경로를 form_input에 적용해 값을 대조하라.
source가 "generated"인 필드는 값 대조 대신 "입력에 없는 요소가 섞였는가"만 본다.
```

## user 지시문 · 페이지

⚠️ **아래 펜스가 2차 검증의 user 메시지에 그대로 실린다.** 2차는 주 검증이라
소개서에 없는 항목 4가지를 추가로 확인한다 — 이미지 슬롯·헤드라인 길이·신청 섹션의
승계값·테마 적용 범위. 넷 다 페이지에만 있는 구조다(§9.3·§9.4).

```text
각 섹션의 source가 가리키는 경로를 form_input에 적용해 값을 대조하라.
추가로 확인할 것:
- image_slot·image_slots 값이 위 목록의 슬롯과 같은가 (빈 문자열은 미업로드로 정상)
- hero.headline이 행사명 그대로이고 40자 이내인가
- apply 내부의 가격요약·행사정보요약이 price·hero와 일치하는가
- 테마 적용으로 섹션 구성·문구·사실정보가 바뀌지 않았는가
```
