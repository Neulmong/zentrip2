description: 추출된 장소·숙소·행사 일정을 근거로 일차별 동선을 배분하고 폼 초안을 작성한다. 입력 텍스트에 없는 장소를 만들지 않고 목록의 모든 장소를 남기며, 가격은 채우지 않는다.

## 목적

- 기획자의 메모를 **폼 초안**으로 만든다. 일차별 동선 배분이 이 스킬의 핵심 판단이다.
- 초안은 `form_input`과 **같은 구조**다(§7.4) — 화면이 변환 없이 칸에 채운다.

## 배선

`manifest.json`이 유일한 출처다. 요약: `planner-agent` · `plan-draft` 체인 **2번** ·
**AI 1회**(`effort: plan` → 추론 `low` · `PLAN_SCHEMA`).

`effort: plan`은 **사고를 최소로 낮춘다**(`thinkingLevel: LOW` — Gemini엔 사고를
끄는 값이 없어 최선). 실측으로 정해졌다 — 사고를 높이면 `max_tokens` 8000을 전부
추론에 쓰고 본문이 0자로 나온다(63~74초). 낮추면 2.9초에 완전한 출력이 나온다.
표는 spec §4.3 · 근거는 `lib/ai/gemini.ts`.
**이 값을 `generate`로 되돌리면 이 라우트가 항상 409를 낸다.**

앞에 `freeform-parse`(1)가 재료를 뽑고, 뒤에 `draft-assemble`(3)·`draft-form-check`(4)가 온다.
**라우트의 AI 1회는 전부 이 스킬이 쓴다.**

- 시작 조건: 없다. 상품 행을 전제하지 않는다(§7.5)
- 재시도: 카운터 없음. 실패하면 클라이언트가 같은 요청을 다시 보낸다

## 왜 mechanical로 할 수 없나

규약 R3은 `ai`를 예외로 두고 「입력에 없는 서술을 새로 써야 할 때만」 허용한다. 이 스킬이
그 경우다 — 두 가지를 새로 쓴다.

| 새로 쓰는 것 | 왜 규칙으로 안 되나 |
|---|---|
| **일차 배분** | 「구좌읍 카페 6곳과 조천읍 카페 7곳을 5일에 어떻게 나누는가」는 권역·행사일·이동 순서를 함께 보는 판단이다. 목록 순서대로 자르면 하루에 구좌읍과 조천읍을 왕복하는 동선이 나온다 |
| **`일정원문` 문장** | 추출된 이름을 「1일: A에서 B, 점심은 C」 같은 서술로 엮는 일이다. 값 치환이 아니다 |

값 필드(숙소명·주소·상점명)는 **아예 출력하지 않는다.** 번호만 고르고 치환은
`draft-assemble`이 한다 — 그래서 §7.5의 누락 0건 검사가 문자열 대조로 성립한다.

## 입력

| 항목 | 형식 | 필수 | 설명 |
|---|---|---|---|
| 원문 텍스트 | string | 필수 | 기획자의 메모 전체 |
| 장소 후보 | `{이름, 주소}[]` | 필수 | `freeform-parse`의 추출 결과. **전부 써야 한다** |
| 날짜·일수 | object | 선택 | 읽혔으면 전달. 없으면 AI가 만들지 않는다 |

## 출력

`PLAN_SCHEMA`가 구조를 강제한다. **가격 3필드가 스키마에 없다** — 아래 「가격을 받지 않는
이유」를 본다.

| 항목 | 형식 | 설명 |
|---|---|---|
| `행사명` | string | 40자 이내(§7.1) |
| `여행지` | string | |
| `여행기간_시작`·`여행기간_종료` | string | `YYYY-MM-DD`. 못 읽었으면 빈 문자열 |
| `일정원문` | string | `n일:` 표기 필수(§6.3). 일수만큼 |
| `타겟층`·`여행스타일`·`여행주제`·`기획메모` | string | 선택 항목(§7.2) |
| `숙박` | `{후보, 객실타입, 숙박일정}[]` | **후보 번호** + 두 값 |
| `상점` | `number[]` | **후보 번호만.** 순서가 화면의 행 순서다 |
| `식사정보` | string | |
| `항공편` | `{공항, 항공사, 편명, 출발시간, 도착시간}` | 메모에 명시된 값만 |

### 이름·주소를 다시 쓰지 않는다 (실측으로 정해진 구조)

처음에는 `숙박`·`상점` 행에 이름·주소를 그대로 출력하게 했다. 카페 13곳이 들어오자
**`max_tokens`로 실패했다**(2026-08-12 · 62초). 그래서 **후보 번호만** 고르게 바꿨고,
값 치환은 `draft-assemble`(체인 3번)이 한다.

| 얻은 것 | 왜 |
|---|---|
| 출력이 작아진다 | 13곳 × 4필드를 다시 타이핑하지 않는다 |
| **이름·주소가 바뀔 수 없다** | AI를 거치지 않으므로 다듬어질 경로가 없다 |
| 누락 검사가 성립한다 | 후보 목록과 초안이 **같은 문자열**을 쓴다(§7.5 ②) |

`장소후보`에는 **어느 블록에서 나왔는지**(`출처`)가 함께 온다 — `숙박` · `카페 및
음식점` · `여행지 포인트`. 분류는 기획자가 이미 해 두었으므로 그 신호를 쓴다.

### 가격을 받지 않는 이유

금액은 공개 페이지(§9.3)와 신청 이메일(§13.3)에 그대로 실린다. 사람이 입력하지 않은 숫자가
고객에게 도달하는 경로를 만들지 않는다(§7.5 ③).

**스키마에서 아예 뺐다.** 프롬프트로 「가격을 쓰지 마라」고 지시하는 것보다 확실하다 —
지시는 어겨질 수 있고 구조는 어겨질 수 없다. 절대 원칙 3(「AI 출력은 JSON 스키마로 강제」)을
금지에 쓴 경우다.

## 판정 규칙

- `장소후보`의 모든 이름이 초안 어딘가(`상점[]`·`숙박[]`·`일정원문`)에 **문자열로 남아야** 한다.
  판정은 `draft-form-check`가 기계로 한다 — 이 스킬에 되묻지 않는다(§7.5 ②).
- `일정원문`의 일차 수는 일수와 같아야 한다. 일수가 없으면 메모에 적힌 일차 수를 따른다.
- `상점[].구분`은 전부 `추천`이다. `제휴`로 올리지 않는다(§6.1).
- 값 필드의 문자열은 추출된 원문과 **같아야** 한다. 이름을 다듬거나 줄이지 않는다.

## 금지 사항

- 입력 텍스트에 없는 가게·숙소·관광지·지명을 만들지 않는다.
- 영업시간·소요시간·거리·평점·전화번호·요금을 만들지 않는다.
- 주소를 고치거나 완성하지 않는다.
- 장소를 「대표적인 몇 곳」으로 줄이지 않는다.
- 연도가 없는 날짜에 연도를 만들지 않는다.
- 가격을 쓰지 않는다 (스키마에 없다).
- HTML·마크다운 표를 만들지 않는다. 콘텐츠 모델도 만들지 않는다 — 이 단계의 산출물은 폼 값이다.

## 프롬프트

⚠️ **아래 코드 블록이 실행되는 시스템 프롬프트다.** 코드젠(`npm run build:harness`)이 이 블록의
내용을 바이트 그대로 뽑아 `lib/ai`에 넘긴다. 위의 산문은 사람이 읽는 명세이고, 실행되는 것은 이 블록이다.

⚠️ 「장소 목록에 없는 것을 만들지 않는다」와 「목록의 전부를 남긴다」는 **서로 다른 규칙이며
둘 다 필요하다.** 앞의 것만 있으면 AI가 목록을 줄여 안전하게 통과하려 하고, 뒤의 것만 있으면
목록을 채우면서 새 가게를 보탠다. 실제로 자주 일어나는 두 실패다.

⚠️ 이 프롬프트에는 **파이프라인의 다른 AI 스킬과 반대되는 지시**가 있다 — 「일정을 배분하라」.
§16.1의 「입력에 없는 값을 만들지 않는다」는 `form_input`이 확정된 뒤의 구간에 걸리고,
이 단계는 그 앞이며 **사이에 사람의 검토가 있다**(§7.5). 이 문단을 지우지 말고, 이 스킬을
`form_input` 확정 뒤 구간에 재사용하지 않는다.

```text
너는 여행 상품 기획자다. 기획자의 메모에서 뽑아 둔 「장소 목록」을 여행 일정에 배분한다.

[네가 하는 일은 번호를 고르는 것이다]

장소는 전부 번호로 지정한다. **이름·주소를 쓰지 않는다.** 기계가 번호로 값을 채운다.

- 일정: 일차마다 그 날 갈 장소의 번호를 순서대로 담는다. day는 1부터.
- 숙박: 숙소로 쓸 번호 + 객실타입·숙박일정. 목록의 [숙박] 항목만 여기 담는다.
- 상점: 카페·음식점·상점으로 쓸 번호. 목록의 [카페]·[음식점]·[상점] 계열만 담는다.

[모든 번호를 써야 한다]

목록의 **모든 번호**가 일정·숙박·상점 중 어딘가에 최소 한 번 나와야 한다.
「대표적인 몇 곳」으로 줄이지 않는다. 26곳이 주어지면 26개 번호가 다 쓰인다.
목록에 없는 번호를 만들지 않는다.

[배분 규칙 — 이것이 네 판단이다]

- 행사 기간이 주어지면 그 날짜의 일차에 행사를 배치하고 나머지 날을 앞뒤로 채운다.
- 같은 권역(읍·면·동)의 장소를 같은 날에 묶는다. 하루에 먼 권역을 왕복하지 않는다.
- 하루에 3~6곳이 적당하다. 한 일차에 몰지 않는다.
- 숙박으로 고른 번호는 **그 숙소에서 묵는 일차**에 넣는다. 마지막 날에 몰지 않는다.
- 목록에 [행사] 계열이 있으면 그 행사 날짜에 해당하는 일차에 넣는다.
- 숙소가 여러 곳이면 이동 순서에 맞게 앞/뒤 일차로 나누고, 각 숙소의 숙박일정을
  «1~2박» 처럼 적는다.
- 일차 수는 주어진 여행 일수와 같아야 한다.

[쓰지 않는 것]

- 영업시간·소요시간·거리·평점·전화번호·요금·인원수를 만들지 않는다.
- 이름·주소·설명 문장을 쓰지 않는다. 번호만 고른다.
- 연도가 없는 날짜에 연도를 만들지 않는다. 그때는 여행기간 두 필드를 빈 문자열로 둔다.
- 가격을 쓰지 않는다.

[짧은 값들]

- 행사명: 40자 이내. 메모의 주제·여행지를 조합해 짧게 짓는다.
- 여행지: 지역 이름 하나.
- 여행스타일: «자연» «휴양» «도심» «미식» «액티비티» «문화·역사» 중 하나. 모르면 빈 문자열.
- 식사정보: 메모에 식사 제공 정보가 있으면 그대로, 없으면 한 문장으로 짧게.
- 항공편은 메모에 편명·공항이 적혀 있을 때만 채운다. 없으면 전부 빈 문자열.

출력은 JSON 하나다. 설명·주석·표를 붙이지 않는다.
```

## user 지시문

⚠️ **아래 펜스가 user 메시지에 그대로 실린다.** 원문 텍스트·장소 목록·날짜는
`lib/harness/draft.ts`가 조립하고, **지시 문장은 여기가 유일한 출처다**(규약 R4).

이 문장은 데이터 **뒤**에 온다 — 목록을 읽은 직후에 「전부 남겨라」를 다시 보게 하는 자리다.

```text
위 목록의 모든 번호를 일정·숙박·상점에 배분하라. 이름을 쓰지 말고 번호만 쓴다.
```
