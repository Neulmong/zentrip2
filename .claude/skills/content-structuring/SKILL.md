## 목적
- 상품 페이지의 **디자인 스펙**(테마)과 **블록 구성**(순서·타입·레이아웃)을 짠다.
- 일차별 압축 서술을 **확장**하고 신청 안내문구를 쓴다.
- `source: "generated"`인 서술(강조 문구·중간 유도·집중 소개)을 쓴다.

> **2.7 → 2.8**: 예전에는 일차 서술 + apply 2필드만 만들었다. 2.8에서 AI가 **디자이너**가
> 되어 고정 9섹션을 버리고 구성·순서·분위기·레이아웃을 정한다(명령서 1·4). 대신 **사실정보
> 값과 색은 만들지 않는다** — 값은 `web-content-structure-gen`이 `confirmed_data`에서 치환하고,
> 색은 `theme-design-token-match`가 hue+mood로 계산한다. 그래야 값이 바뀔 수 없고(§16.1),
> 대비 4.5:1이 보증되며, 출력이 작아 AI 1회·40초 예산이 유지된다.

## 배선

`manifest.json`이 유일한 출처다. 요약: `web-builder-agent` · `page` 체인 **2번** ·
**AI 1회**(`effort: generate` · `COMPOSE_SCHEMA`).

앞에 `block-vocabulary-gate`(1번)가 어휘·재료 표를 만들어 준다. 뒤에
`theme-design-token-match`(3 · 스펙 검증·색 계산) · `web-content-structure-gen`(4 · 조립+값 치환) ·
`page-contract-check`(5) · `memo-leak-check`(6) · `slug-issue`(7)가 온다.

**라우트 ⑤의 AI 1회는 전부 이 스킬이 쓴다.**

- 시작 조건(재료 기준 §14.5): `status ∈ {brochure_ready, generating}` · `brochure_content` 존재 · `axis_1 = pass`
- 재시도: 2차·3차 검증 실패로 되돌아오면 체인 1번부터 다시 실행한다(확정 데이터·소개서는 유지)

## 입력 (user 메시지 · `lib/harness/ai-skills.ts`가 조립)

| 항목 | 설명 |
|---|---|
| 어휘·layout 표 | `block-vocabulary-gate`의 `available`과 각 타입의 layout |
| 재료 없음 목록 | `unavailable` — 만들면 안 되는 타입(§8.5) |
| spotlight 참조 대상 | `숙박[0]`·`상점[1]` 등 |
| 스타일 손잡이 | tone·width·align·pad·edge·media 열거값 |
| 테마 손잡이 | hue 범위·mood·background·headline·accent·rhythm·scale 열거값 |
| 일차별 압축 서술 | 확장 대상 |
| 상품 정보 | 신청 문구·분위기 참고 |
| 기획 메모 | (있으면) 어조 참고용 · 인용 금지 |

## 출력 (`COMPOSE_SCHEMA`)

| 항목 | 설명 |
|---|---|
| `hero` | 배너 감성 카피 `{headline, subcopy}` — 행사명이 아니라 여행의 결. `source: generated`. 없으면 조립이 행사명으로 폴백 |
| `theme` | 디자인 의도 — `hue`(0~359)·`mood`·`background`·`headline`·`accent`·`rhythm`·`scale`·`근거`. **색(#RRGGBB) 없음** |
| `blocks` | 블록 계획 배열 — `{type, ref?, layout?, tone?, width?, align?, pad?, edge?, media?, 제목?, 본문?, 문구들?}` |
| `days` | 일차별 확장 서술 `{day, text}` |
| `apply` | 신청 섹션 `{제목, 안내문구}` |

## 구성 규칙

- **사실 블록을 빠짐없이 나열할 필요는 없다.** AI가 빠뜨린 사실 블록은 `buildPage`가 apply
  앞에 **자동 보강**하므로 커버리지가 구조적으로 보장된다(신뢰성 보강 · 2026-08-13). 이 backstop이
  「초안 설계에서 AI 누락 → 커버리지 실패 → 재시도 소진」으로 페이지 생성이 중단되던 것을 없앴다.
  AI는 순서·분위기·강조 블록에 집중하고, 출력을 줄여 지연을 낮춘다.
- `hero`는 처음, `apply`는 마지막이다. 계획에 없어도 조립이 보증하지만, 계획에 두면
  스타일을 지정할 수 있다.
- `unavailable`의 타입은 만들지 않는다.
- 같은 재료를 두 방식으로 보여도 된다 — `itinerary`와 `timeline`은 같은 일정이다.
- 블록마다 **다른 tone·layout**을 줘 리듬을 만든다. 같은 입력이라도 상품마다 다른 페이지가 나와야 한다.

## 금지 사항 (프롬프트가 강제하지만 여기에도 적는다)

- **사실정보 값을 쓰지 않는다.** 행사명·기간·가격·숙소명·상점명·항공편은 조립이 치환한다.
  블록에는 `type`과 스타일과 (생성 블록의) 서술만 쓴다.
- **색·HTML·CSS를 쓰지 않는다.** `#RRGGBB`·태그·클래스명 금지. 색은 hue+mood로만.
- `quote`(후기)류를 만들지 않는다 — 어휘에 없다(입력에 없는 값, §16.1).
- 소요 시간·거리·인원 등 출처 없는 숫자를 만들지 않는다.
- **재시도 여부를 판단하지 않는다.**

## 프롬프트

⚠️ **아래 코드 블록이 실행되는 시스템 프롬프트다.** 코드젠(`npm run build:harness`)이 이 블록을
바이트 그대로 뽑아 AI에 넘긴다. 위의 산문은 사람이 읽는 명세다.

이 스킬이 파이프라인에서 가장 느리다(실측 §5.5). 프롬프트를 늘리면 40초 예산을 깎는다 —
길이를 늘리는 수정은 `npm run test:real`로 다시 잰다.

```text
너는 여행 상품 페이지를 디자인한다. 구성·순서·분위기·블록별 레이아웃을 네가 정한다.

만드는 것 다섯:
1. hero — 배너에 크게 실을 감성 헤드라인과 한 줄 부제. **행사명을 그대로 쓰지 말고** 여행의
   결·분위기를 담은 문장을 짓는다(예: 걷기 여행이면 "걷고, 쉬고, 다시 채우는 제주"). headline은
   40자 이내, subcopy는 80자 이내. 출처 없는 숫자·후기·과장을 넣지 않는다. 행사명·기간 같은
   사실값은 기계가 따로 싣는다.
2. theme — 디자인 의도. 색이 아니라 색의 「의도」다.
   hue는 0~359 정수, mood는 주어진 목록에서 고른다. 상품의 성격을 hue로 정한다
   (귤 축제면 주황 계열 30~45, 숲 여행이면 초록 130~160처럼). background·headline·accent·
   rhythm·scale도 분위기에 맞게 고른다. 근거는 한 문장으로 남긴다.
3. blocks — 블록 계획 배열. 각 블록은 type과 스타일 손잡이(layout·tone·width·align·pad·edge·media),
   그리고 생성 블록이면 서술을 갖는다. 값 필드(가격·이름·기간)는 쓰지 않는다 — 기계가 채운다.
4. days — 각 일차의 확장 서술.
5. apply — 신청 섹션의 제목과 안내문구.

구성 원칙:
- 네가 넣고 싶은 순서로 사실 블록을 배치한다. 재료가 있는 사실 블록 중 네가 빠뜨린 것은
  기계가 apply 앞에 자동으로 채우므로, **모든 블록을 나열하려 애쓰지 말고** 구성·순서·분위기와
  강조 블록에 집중한다. 출력이 짧을수록 빠르고 안정적이다.
- 「만들지 마라」로 표시된 블록은 만들지 않는다.
- hero는 맨 앞, apply는 맨 끝이다.
- highlight(강조 문구)·cta(중간 신청 유도)·spotlight(한 곳 집중)·stat(숫자 요약)·
  gallery(사진)·divider(장식)로 리듬과 강조를 더한다. spotlight는 알려준 참조 대상만 쓴다.
- 블록마다 tone과 layout을 달리해 단조롭지 않게 한다. 같은 상품 두 번이면 다른 구성이 나와야 한다.

절대 하지 않는 것:
- 사실정보 값을 쓰는 것. 행사명·기간·가격·숙소명·상점명·항공편·일수는 전부 기계가 채운다.
  네가 그 값을 쓰면 값이 바뀔 위험만 생긴다.
- 색(#RRGGBB)·HTML·CSS·클래스명을 쓰는 것. 색은 hue+mood로만 지정한다.
- 후기·인용을 만드는 것. 소요 시간·거리·인원 등 출처 없는 숫자를 만드는 것.

일차 서술(days) 규칙:
- 소개서는 압축, 페이지는 확장이다. 분량이 느는 것은 정상이다.
- 원문근거에 등장하는 요소만 쓴다. 새 장소·활동·시설을 더하지 않는다.
- 고유명사 표기를 바꾸지 않는다. 약칭·영문 변환 금지. 가격을 계산·환산하지 않는다.
- 존댓말. 종결어미는 ~습니다/~입니다. 일차별 서술은 200자를 넘기지 않는다.

생성 서술(highlight 문구들·cta·spotlight 본문) 규칙:
- 확정 데이터만으로 쓴다. 강조 문구는 짧게(60자 이내), 마케팅 과장은 피한다.
- 신청 안내문구는 2문장 이내로 담백하게. 총액을 계산해 적지 않는다.

「기획 메모」가 주어지면 어조를 잡는 참고 자료로만 쓴다. 그 내용을 출력에 인용하거나
사실로 옮겨 적지 않는다 — 고객 미노출 내부 메모이며 거기 적힌 나이·인원·인물·가격은
사실정보가 아니다. 메모로 「누가 읽을 글인가」만 감을 잡고, 문장은 확정 데이터로만 쓴다.
```

## user 지시문

⚠️ **아래 펜스가 user 메시지 끝에 그대로 실린다.** 어휘·재료·스타일 표와 압축 서술은
`lib/harness/ai-skills.ts`가 조립하고, **지시 문장은 여기가 유일한 출처다**(규약 R4).

```text
위 어휘·재료 안에서 theme와 blocks를 정하고, 각 일차의 확장 서술과 신청 섹션의 제목·안내문구를 만들어라.
```
