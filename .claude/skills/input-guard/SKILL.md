name: input-guard
description: 웹 폼 입력의 관문 검사를 수행한다. 필수 폼 그룹 6개 충족 여부를 재확인하고, 입력 문제로 중단할 때 사유 문장을 작성한다. 값을 임의로 생성·추정·보완하지 않는다.
---

## 목적
- 폼·서버 validation을 통과한 입력이 확정 데이터표를 만들 준비가 됐는지 최종 확인한다.
- 입력 문제로 `input_error`가 될 때 기획자가 무엇을 고쳐야 할지 명시한 사유 문장을 만든다.

> **통합 이력**: 2.2에서 `required-field-check`·`rejection-reason-writer`·`natural-language-extraction` 3개를 이 스킬로 통합했다. 웹 폼 도입으로 세 스킬 각각의 일이 한두 줄로 줄어들어 개별 스킬로 유지할 실체가 없어졌기 때문이다. 자유 텍스트 파싱 역할은 `itinerary-decomposition`이 이어받았다.

> ⚠️ **분할 이력 (하네스 규약 R2).** 2.2의 이 스킬은 관문 검사와 **선택 항목 채움**을
> 함께 했다. 「검사한다」와 「채운다」는 두 가지 일이므로 스킬을 나눴다.
> 채움은 **`optional-field-fill`** 이 담당하며 `decompose` 체인 1번이다.
> 이 스킬은 **아무 값도 채우지 않는다.** 아래 `## 검사 대상`의 선택 항목 표는
> 무엇이 미입력 허용인지 판단하기 위한 참조이며, 채우는 주체가 아니다.

## 배선

`manifest.json`이 유일한 출처다. 요약: `intake-agent` · **`products`(라우트 ①)** ·
**AI 0회** · `impl: form-validation#validateFormInput`.

**`decompose` 체인에 있지 않다.** 라우트 ①은 상품 행을 **만드는** 라우트라
`runStep`·`runAgent`의 전제(기존 행·시작 조건·조건부 갱신·카운터)가 성립하지 않는다.
매니페스트가 `driven_by: "route"`로 이를 선언하며, 라우트가 impl을 직접 호출한다.

같은 검사가 `PATCH /form-input`(§14.4 #17)에서도 실행된다 — 입력 재제출 경로다.
그 라우트는 아직 매니페스트에 등록돼 있지 않다(후속 과제).

- 실행 시점: 상품 등록 1회당 1회. 행을 만들기 **전**에 판정한다
- 위반 시: **400.** 행을 만들지 않는다 — 만들고 나서 거절하면 고아 행이 남는다
- 실행하지 않는 경우: 없음. 등록·재제출은 항상 이 판정을 거친다

## 입력

| 항목 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `form_input` | object(JSON) | 필수 | 사용자 원본 폼 입력. **모든 검증의 기준값** |
| 여행기간 일수 | number | 필수 | 시작일·종료일에서 계산된 값 |

```json
{
  "form_input": {
    "행사명": "제주 올레 바람 여행",
    "여행지": "제주",
    "여행기간_시작": "2026-03-14",
    "여행기간_종료": "2026-03-17",
    "일정원문": "1일: 김해공항 출발, 올레 7코스 걷기…",
    "숙박": [
      { "숙소명": "롯데호텔 제주", "위치": "중문", "객실타입": "디럭스룸", "숙박일정": "1~2박" },
      { "숙소명": "성산 한옥스테이 고요", "위치": "성산읍 고성리", "객실타입": "", "숙박일정": "3박" }
    ],
    "상점": [
      { "상점명": "제주 로컬 기념품 숍", "구분": "제휴", "위치": "", "상점정보": "여행객 10% 할인" },
      { "상점명": "종달달", "구분": "추천", "위치": "구좌읍 종달로 60-12", "상점정보": "" }
    ],
    "가격_성인": "120000원", "가격_아동": "해당 없음", "가격_기타": "항공료 별도",
    "식사정보": "조식 3회, 중식 2회",
    "타겟층": "", "여행스타일": "자연", "항공편_항공사": ""
  },
  "여행기간_일수": 4
}
```

**`숙박`·`상점`은 객체 배열이고 1건 이상이다**(spec §7.4). 행이 0건이면 필수 폼 그룹
미충족이므로 `입력오류`다. 행 안의 빈 문자열은 선택 필드의 정상 상태이며, 채움은
`optional-field-fill`이 라우트 ②에서 한다.

## 출력

| 항목 | 형식 | 설명 |
|---|---|---|
| 판정 | `"통과"` \| `"입력오류"` | 관문 통과 여부 |
| 누락 항목 | object | `{필드명: 사유문장}`. 통과면 빈 객체 |

**채움 결과를 반환하지 않는다.** 선택 항목을 `추후 추가 예정`으로 채우는 것은
`optional-field-fill`의 일이며 라우트 ②에서 실행된다(규약 R2).

```json
{
  "판정": "통과",
  "누락항목": {}
}
```

`입력오류`인 경우 — 필드마다 한 문장씩, **모아서** 반환한다:

```json
{
  "판정": "입력오류",
  "누락항목": {
    "상점정보": "상점정보가 비어 있어 상품을 만들 수 없습니다. 필수 항목입니다. 입력 화면에서 '제휴상점 > 상점정보'를 채운 뒤 다시 제출해 주세요."
  }
}
```

첫 위반에서 멈추지 않는다 — 기획자가 한 번에 다 보고 고쳐야 한다.

## 산출물
- 파일 산출물 없음. 반환값만 intake-agent에 전달한다.
- 전달 대상
  - `통과` → intake-agent가 `채움결과`를 반영하고 `data-normalization`으로 넘긴다.
  - `입력오류` → intake-agent가 `status = input_error`, `failure_reason = 사유문장`으로 확정하고 **422**를 반환한다. `itinerary-decomposition` 이후 단계로 진입하지 않는다.
- 로그: `normalization_validated` 항목의 입력·출력에 이 반환값이 원본으로 기록된다.

## 검사 대상

### 필수 폼 그룹 6개 (spec §7.1)

| 폼 그룹 | 필드 |
|---|---|
| 행사정보 | 행사명, 여행지, 여행기간(시작·종료) |
| **일정** | 일정 원문 |
| 숙박 | **행 1건 이상** · 행마다 숙소명, 위치 |
| 상점 | **행 1건 이상** · 행마다 상점명, 구분 |
| 가격 | 성인, 아동, 기타 |
| 식사 | 식사정보 |

**`객실타입`·`상점정보`는 행의 필수 필드가 아니다**(spec §7.2). 행마다 요구하면 객실이
미확정인 숙소나 설명 없는 가게를 목록에서 빼야 하고, 목록에서 빠지는 것이 빈칸으로
남는 것보다 나쁘다 — 미입력 표기(§6.1)가 이미 그 빈칸을 처리한다.

> **주의**: `일정`은 폼 그룹이지만 확정 데이터표의 최상위 데이터 키가 아니다. `행사정보.일정원문`에 저장된다(spec §6.0).

### 선택 항목 4개

| 항목 | 저장 경로 |
|---|---|
| 타겟층 | `행사정보.타겟층` |
| 여행스타일 | `행사정보.여행스타일` |
| 여행주제 | `행사정보.여행주제` |
| 기획메모 | `행사정보.기획메모` — **고객 미노출 · 채움 대상 아님**(§6.1) |
| 객실타입 · 숙박일정 | `숙박[i].객실타입` · `숙박[i].숙박일정` (행마다) |
| 상점 위치 · 상점정보 | `상점[i].위치` · `상점[i].상점정보` (행마다) |
| 항공편 | `항공편.공항`·`항공사`·`편명`·`출발시간`·`도착시간` (5개 하위 필드 전부) |

## 판정 규칙

- 필수 폼 그룹의 필드 중 **하나라도** 비어 있으면 `입력오류`다. "모두 비어 있을 때"가 아니다.
- `숙박`·`상점`이 **0건이면** `입력오류`다. 배열이 비어 있는 것은 그룹 미충족이다(§7.4).
- 배열 행의 오류 키는 `source` 경로와 같은 표기(`숙박[0].숙소명`)를 쓴다 — 화면이 그 키로 칸을 찾는다.
- `가격.기타`는 필수 그룹에 속하지만 **0자를 허용**한다(spec §7.1). 빈 문자열이어도 누락으로 보지 않는다.
- `가격.아동`이 `해당 없음`이면 정상 값이다. 누락으로 보지 않는다.
- 선택 항목이 비어 있으면 **실패로 처리하지 않고** 문자열 `추후 추가 예정`으로 채운다. 확인 질문 절차는 없다(폼 UI가 그 역할을 대체한다).
- 항공편은 하위 5개 필드 중 **하나라도 비어 있으면 그 필드만** `추후 추가 예정`으로 채운다. 그룹 전체를 비우거나 전체를 채우는 방식이 아니다.
- 값을 추정·보완·생성하지 않는다. 허용된 채움은 `추후 추가 예정` 문자열 하나뿐이다.
- **재시도 여부를 판단하지 않는다.** 판정과 사유만 반환한다.
- 필수값 누락은 프론트엔드·서버 validation이 이미 차단하므로 여기서 `입력오류`가 나오는 것은 우회 호출·데이터 손상 등 예외 상황이다. 그 경우에도 후속 단계로 진입시키지 않는다.

## 사유 문장 작성 규칙

`입력오류`일 때만 작성한다. 세 문장 구조를 고정한다.

```text
{누락 항목명}이(가) {문제 상태}이어서 상품을 만들 수 없습니다.
{왜 필요한지 한 문장}.
입력 화면에서 '{폼 그룹} > {필드명}'을(를) {할 일}한 뒤 다시 제출해 주세요.
```

| 규칙 | 내용 |
|---|---|
| 항목명 표기 | 폼 화면에 보이는 라벨을 그대로 쓴다. 내부 키(`가격_성인`)를 노출하지 않는다 |
| 위치 안내 | `'{폼 그룹} > {필드명}'` 형태로 어디를 고쳐야 하는지 명시한다 |
| 금지 | 누락 항목을 추측해 예시 값을 제시하지 않는다. "예: 120000원처럼 입력하세요" 같은 값 제안은 하지 않는다 |
| 금지 | 여러 항목이 누락되면 하나로 뭉뚱그리지 않고 항목별로 한 문단씩 쓴다 |
| 대상 | **입력 문제만** 대상이다. 검증(0·1·2·3차) 실패는 반려가 아니라 재시도이므로 이 스킬이 사유를 쓰지 않는다 |

### 일차 분해 실패 시의 사유 문장

`itinerary-decomposition`이 실패를 반환하면 intake-agent가 이 스킬을 **한 번 더** 호출해 사유 문장만 받는다.

| 실패 유형 | 사유 문장 |
|---|---|
| 원문 일차 > 여행기간 | `일정에 {n}일차까지 적혀 있지만 여행기간은 {m}일입니다. 일정의 일수와 여행기간이 같아야 합니다. 입력 화면에서 '여행기간' 또는 '일정 > 일정 원문'을 맞춘 뒤 다시 제출해 주세요.` |
| 일차 구분 식별 불가 | `일정에서 일차 구분을 찾을 수 없습니다. 어느 내용이 몇 일차인지 알 수 없으면 일정을 임의로 나눌 수 없습니다. 입력 화면에서 '일정 > 일정 원문'에 '1일:', '2일:'처럼 일차 구분을 넣어 다시 제출해 주세요.` |
