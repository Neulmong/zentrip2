# 하네스 전환 계획 — 스킬·에이전트를 런타임 실행 근거로 만든다

**권위:** `spec.md` 2.6이 여전히 유일한 권위다. 이 문서는 spec을 바꾸지 않고, spec을 **어디에 적어두는지**를 바꾼다.

---

> ## 📌 이어서 작업하려면 **§7부터** 읽는다
>
> **§0~§6은 계획 문서이고 전환은 이미 끝났다.** 설계 판단의 근거로 남겨둔 것이며,
> 그 안의 수치(스킬 16개·라우트 7개·AI 6회…)와 「지금 건드리지 않는다」류의 문장은
> **8/12 낮 시점의 기록이다.** 현재 상태는 §7이 갖는다.
>
> | 궁금한 것 | 어디 |
> |---|---|
> | 지금 어떻게 돌아가나 | §7.1 |
> | 무엇이 검증됐나 | §7.2 |
> | **무엇이 남았나** | **§7.3 ⑤** |
> | 처음 여는 사람이 할 일 | §7.4 |
>
> 전환 당시(8/12 낮) 상태: 라우트 7 · 스킬 21 · AI 6회.
> **현재(8/12 밤): 라우트 10 · 스킬 24 · AI 5회 · 검사 155건 · 미구현 0.**

## 0. 전환 착수 시점의 상태 (2026-08-12 낮 · 히스토리)

| 대상 | 런타임 사용 |
|---|---|
| `.claude/skills/` 16개 | **0건.** `app/`·`lib/`·`components/` 어디도 참조하지 않는다 |
| `.claude/agents/` 5개 | **0건.** 서브에이전트를 스폰하는 라우트가 없다 |
| DeepSeek | 6곳 — `/decompose`·`/brochure`·`/validate-brochure`·`/page`·`/validate-page`·`/validate-consistency` |

스킬의 규칙은 이미 TS 순수 모듈로 **흡수**되어 있다(`lib/pipeline/*`, `lib/logging.ts`, `lib/orchestrator.ts`).
즉 지금 구조는 "스킬을 안 쓴다"가 아니라 **"스킬을 사람이 손으로 코드에 베껴 넣었다"** 다.
전환의 목표는 베낀 사본을 지우고 원본을 실행하게 만드는 것이다.

### 이미 있는 발판 3개

1. 6개 AI 호출이 전부 `lib/ai`의 provider 중립 인터페이스 하나(`ai().call`)를 통과한다 — 갈아끼울 지점이 1곳이다.
2. 각 AI 호출이 이미 `label`로 **스킬 이름**을 붙이고 `execution_logs`에 남긴다
   (`itinerary-decomposition`·`content-structuring`·`consistency-check`·`fact-check-1/2`·`intro-overview`).
3. `runStep`(`lib/orchestrator.ts`)이 재시도 카운터·409·이상 플래그·조건부 갱신을 이미 spec 2.6대로 처리한다.

### 넘을 벽

`.claude/**`는 **Claude Code CLI만 읽는 파일**이다. Vercel 서버리스 함수는 이 디렉터리를 트레이싱하지 않으며
(어느 모듈도 import하지 않으므로 번들에 포함되지 않는다) SKILL.md를 해석해 실행하는 능력도 없다.
따라서 **전달 경로**와 **의미 해석**을 우리가 만들어야 한다.

## 1. 전달 — 빌드 타임 코드젠

`scripts/build-harness.mts`가 `.claude/**`를 읽어 `lib/harness/generated/registry.ts`를 생성한다.
`prebuild`·`predev`에 물린다. 산출물은 커밋한다(빌드에서 재생성하고 drift를 검사한다).

`fs.readFile`을 런타임에 쓰지 않는 이유 3가지:

1. **번들 트레이싱** — `.claude/**`는 import되지 않아 Vercel 번들에 없다. `outputFileTracingIncludes`로 우겨넣을 수는 있지만 핫 패스에 비동기 IO가 들어간다.
2. **캐시 적중** — 시스템 프롬프트는 요청 간 **바이트 단위로 동일**해야 한다(실측 913 중 896 적중). 동결된 문자열 상수는 이를 보장하고, 파일 읽기는 EOL·인코딩 드리프트 위험을 안는다. **이 저장소는 Windows다** — 코드젠은 CRLF를 `\n`으로 정규화해 프롬프트 바이트를 고정한다.
3. **실패 시점** — SKILL.md가 망가졌으면 **빌드가 죽는다.** 데모 중 런타임 500보다 낫다.

## 2. 의미 — 매니페스트와 프롬프트의 분리

SKILL.md 본문은 이미 두 종류의 내용이 섞여 있다.

| 섹션 | 성격 | 하네스에서의 용도 |
|---|---|---|
| `## 목적`·`## 판정 규칙`·`## 금지 사항`·`## 출력`·규칙 표 | AI에게 줄 지시 | **시스템 프롬프트 본문** |
| `## 실행 조건`(호출 주체·AI 호출 횟수)·`## 산출물`(로그·전달 대상) | 배선 정보 | **매니페스트** |

그래서 프롬프트에 배선 정보가 섞이지 않게, 매니페스트가 **어느 섹션을 프롬프트로 쓸지 지정**한다.
코드젠은 지정된 `##` 섹션만 원문 그대로 뽑아 이어붙인다. 문서 하나가 사람과 런타임 양쪽을 만족한다.

### 매니페스트는 `.claude/harness/manifest.json` 하나다 (확정 · 2026-08-12)

frontmatter에 `harness:` 키를 넣는 방식을 검토했으나 **중앙 파일 하나로 결정**했다. 이유 3가지:

1. **불변식이 그래프 수준이다.** 라우트당 AI 예산, 체인 순서, 고아 스킬, `spec` 스킬이 체인에 섞였는지 —
   전부 여러 스킬을 동시에 봐야 판정된다. 16개 파일에 흩어져 있으면 검사기가 전부 읽어 재조립해야 한다.
2. **YAML 파서가 필요 없다.** `package.json`에 YAML 의존성이 없다. JSON이면 `JSON.parse`로 끝나고,
   SKILL.md에서는 frontmatter를 건너뛰고 `##` 섹션만 뽑으면 되므로 파서를 쓸 일이 아예 없다.
3. **Claude Code의 frontmatter 미지 키 처리에 의존하지 않는다.** 이틀 남은 일정에서 확인되지 않은
   전제를 21개 문서에 심지 않는다.

`kind`가 세 값인 이유: 20개 스킬이 같은 성격이 아니다.

| `kind` | 개수 | 성격 |
|---|---:|---|
| `mechanical` | 11 | AI 0회. `impl`이 가리키는 순수 함수가 실행된다 |
| `ai` | 5 | SKILL.md의 지정 섹션이 **시스템 프롬프트 그 자체**다 |
| `spec` | 4 | `runStep`·`logging.ts`가 이미 수행하는 규정. **체인에서 실행되지 않는다** |

`spec`을 체인에 끼우면 로그가 두 번 쌓인다. 하네스는 이들을 실행하지 않고 `implemented_by` 대상이
계속 존재하는지만 검사한다.

`routes`가 맵인 이유: `validator-agent` 하나가 라우트 3개(`validate-brochure`·`validate-page`·
`validate-consistency`)를 담당한다. 에이전트를 3개로 쪼개면 문서의 통일성이 깨지므로, 문서 1개에 라우트 3개를 둔다.

### 라우트가 7개가 됐다

`POST /api/products`(라우트 ①)를 하네스에 넣었다. `input-guard`의 자리는 폼 제출 라우트이지
분해 라우트가 아니다 — 2.2 문서가 이 스킬을 Step 02에 배치한 것은 웹 폼이 없던 시절의 배선이다.
`ai_budget: 0`인 라우트가 하나 생기며, 이것이 규약 R3(mechanical이 기본)의 실례가 된다.

## 3. 런타임

```
lib/harness/
  generated/registry.ts   ← 코드젠 산출물. 동결된 프롬프트 문자열 + 파싱된 매니페스트
  loader.ts               ← 매니페스트 타입·조회. registry 외부를 읽지 않는다
  impls.ts                ← mechanical 스킬 이름 → 순수 함수 등록표
  run.ts                  ← runAgent()
```

`runAgent(agentName, routeKey, product)`:

1. 매니페스트를 로드한다. 없으면 **throw** (빌드 검사를 통과했다면 발생하지 않는다).
2. `skills`를 선언 순서대로 실행한다.
3. **각 스킬 실행 전에 누적 `ai` 합계를 `ai_budget`과 대조하고, 초과하면 throw.**
   절대원칙 1(1요청 1AI호출)이 지금은 사람이 지키는 규율인데, 하네스에서는 **코드가 강제한다.**
4. `kind: ai` 스킬은 registry의 동결 프롬프트를 `system`으로, 선언된 schema·effort로 `lib/ai`를 호출한다.
5. `kind: mechanical` 스킬은 `impls.ts`의 함수를 호출하고, 선언된 `asserts`를 반환값에 대해 검사한다.
6. 결과를 `StepOutcome`으로 변환한다.

### 손대지 않는 것

`lib/orchestrator.ts`(`runStep`)·`lib/logging.ts`·`lib/policy.ts`·`lib/ai/*`·`lib/client/run-pipeline.ts`.

재시도 카운터 4종·409 `reason` 5종·이상 플래그 5종·조건부 갱신·클라이언트 재개 표는 이미 spec 2.6대로
구현되고 4개 스위트로 검증됐다. 하네스는 `runStep`의 **`work` 콜백 안쪽만** 대체한다.
**이것이 이틀 안에 되는 유일한 이유다.** 하네스가 상태 기계까지 삼키면 검증을 처음부터 다시 해야 한다.

### 전환 후 라우트

```ts
export const maxDuration = 60

export async function POST(req: NextRequest, ctx: { params: Promise<{ id: string }> }) {
  const { id } = await ctx.params
  return runStep(
    agentStepConfig('intake-agent', 'decompose', { productId: id, clientUpdatedAt: await readUpdatedAt(req) }),
    (p) => runAgent('intake-agent', 'decompose', p),
  )
}
```

`decompose/route.ts`는 148행에서 약 12행이 된다. **라우트 코드에 프롬프트가 없다** — 이것이 판정선이다.

### 프롬프트의 이동

`lib/pipeline/ai-contracts.ts`의 `*_SYSTEM` 상수 6개를 **삭제**하고 SKILL.md 본문으로 옮긴다.
`*_SCHEMA`와 `interface`는 TS에 남긴다 — 타입과 짝이어야 하고, SKILL.md는 스키마의 **이름만** 지정한다.

`intro-overview` 라벨에 대응하는 스킬이 없다. `intro-content-fill`의 `kind`를 `ai`로 올려 흡수한다
(§8.7에서 `source: "generated"`인 필드는 `overview.핵심일정` 하나뿐이므로 이 스킬의 자연스러운 일이다).

`consistency-check`(3차)는 기계 대조로 내릴 여지가 있다 — 페이지가 소개서 값을 코드로 승계하므로
> **⚠️ 이 판단은 뒤집혔다 — §7.3 ③을 보라.** 아래는 8/12 낮 시점의 기록이다.
> 실제로는 `source` 경로를 조인 키로 쓰면 기계 대조가 성립하고, 그렇게 전환했다(AI 6 → 5회).

대조가 거의 항등식이다. 성공하면 대본당 AI 6회 → 5회. **지금 건드리지 않는다:** 3차 축의 의미와
§20 1:15의 4축 검증 배지가 바뀌므로, 데모 대본이 검증된 상태를 흔들 수 없다.

## 5. 검증 — 하네스가 진짜인지 증명한다

`npm run test:harness` 신규. 4개 검사:

되돌릴 시간이 없는 것이 최대 리스크다. 그래서:

- **커밋 1개 = 라우트 1개.** 6개를 한꺼번에 바꾸지 않는다. 각 커밋 뒤 `test:demo`를 돌린다.

  현재 프롬프트로 §20 대본 통과와 DeepSeek 캐시 적중이 실측됐다. 하네스 전환과 프롬프트 변경을
  같은 커밋에 넣으면 실패했을 때 원인을 분리할 수 없다.
- `git tag demo-fallback`을 전환 시작 전 커밋에 붙인다. 8/13 오후까지 `test:demo`가 안 통과하면 그 태그로 시연한다.

### 남는 정직한 한계

`kind: mechanical` 스킬에서 SKILL.md는 **프롬프트가 아니라 명세 + 배선**이다. 실제 변환은 TS 함수가 한다.
문서를 고쳐도 `impl` 함수의 동작이 자동으로 바뀌지는 않는다 — 바뀌는 것은 체인 순서, 배선, `asserts` 검사다.
AI 호출 0회를 유지하려면(절대원칙 1·§4.2) 이 한계는 피할 수 없다. 모든 스킬을 AI로 돌리면
요청당 호출이 3배가 되고 페이지 확장이 이미 §5.5의 20초 임계에 붙어 있으므로 데모가 깨진다.
`kind: ai` 스킬 6개에서는 SKILL.md가 프롬프트 **그 자체**이며, 이쪽이 문서가 완전히 load-bearing인 지점이다.

`lib/edit-contract.ts`가 가장 큰 구멍이었다 — 편집 저장 규칙이 코드에만 있었다.
**생성 시 4종 / 저장 시 6종**이 갈리는 지점이 거기이므로, 새 SKILL.md가 그 관계를
명시하고 `page-contract-check`와 서로를 가리키게 했다.

**`agent: null`을 도입했다.** 편집 저장·주소 변경은 담당 에이전트가 없다 —
에이전트 5종은 전부 생성·검증 주체이고 편집은 그 어느 쪽도 아니다. 억지로 배정하면
그 에이전트 문서가 자기가 하지 않는 일을 설명하게 된다. 대신 `driven_by: "route"`와
짝이어야 하며 코드젠·검사기가 검산한다.

**러너를 만들지 않았다.** `driven_by: "route"` 스킬은 `runChain`이 돌리지 않으므로
`impls.ts` 러너를 쓰면 실행되지 않는 코드가 된다. 검사기를 만족시키려고 죽은 코드를
쓰게 하는 것이 더 나쁘다 — 대신 §9-1이 「그 라우트가 선언한 impl을 실제로 부르는가」를 본다.

### ③ 남은 3건 — **전부 완료 (2026-08-12 밤)**

셋 다 「AI에게 보내는 바이트가 바뀌는」 변경이라 한 묶음으로 처리했다.

| # | 항목 | 결과 |
|---|---|---|
| 1 | `consistency-check`를 mechanical로 | **AI 6 → 5회.** 두 콘텐츠 모델이 같은 `source` 경로를 쓰므로 그것을 조인 키로 기계 대조가 된다 |
| 2 | user 지시문을 SKILL.md로 | **R4 완결 · 미구현 0건.** 변형키(`brochure`/`page`)를 도입해 `fact-check`의 두 지시를 분리 |
| 3 | spec §6.3 판정 3단계 | **구현.** AI가 `핵심표현`을 신고하고 **기계가 근거를 대조해 판정한다** |

#### 「재실측이 필요하다」는 전제가 틀렸다

이전 판본은 셋 다 캐시 적중을 깨므로 `probe:deepseek` 재실측이 필요하다고 적었다.
**DeepSeek 컨텍스트 캐시는 최장 공통 접두를 잡고 system이 앞에 온다** — user 쪽 변경은
system 프리픽스 적중을 깨지 않는다. 2번은 문장을 바이트 그대로 옮겼으므로 user 바이트도
동일하다. 3번만 system 프롬프트가 바뀌어 해시가 갱신됐다(`4f11348221a9` → `1b9a0793e09a`).

#### 3단계를 한 호출 안에서 성립시킨 방법

spec §6.3은 3단계 주체를 「AI(`itinerary-decomposition`의 **호출 1회 안에서**)」로 못박는다.
그런데 2단계는 AI 출력(`내용`)에 대해 도는 검사라 **호출 전에는 후보가 없다.**
한 호출 안에서 되게 하려면 AI가 **미리 신고**하는 수밖에 없다.

| 주체 | 하는 일 |
|---|---|
| AI | `내용`에 쓴 장소·시설·활동·고유명사를 `핵심표현`으로 신고 |
| **기계** | 신고된 표현이 `원문근거`·다른 확정 값에 있는지 대조 → **판정** |

**판정 주체가 기계다.** AI는 근거를 제시할 뿐 통과 여부를 정하지 않으므로 §6.3 마지막
문단(「AI가 자기 생성물을 자기가 검사하는 구조에만 의존하지 않는다」)을 지킨다.

2단계 `위반후보`는 계속 표시만 한다 — `extractNouns`가 동사 활용형을 명사구로 오인하기
때문이다. 신고 목록에는 그 오인이 없다. **그것이 3단계를 하드 실패로 쓸 수 있는 이유다.**

실측(`test:demo`): AI가 `["김해공항","올레 7코스"]`·`["성산일출봉","해녀박물관"]`처럼
고유명사만 정확히 신고했고 활용형은 하나도 섞이지 않았다. 「추후 추가 예정」 일차는 빈 배열.

### ③-b `day` 형식 결함 — **고침 (2026-08-12 밤)**

3단계 데이터를 들여다보다 발견했다. AI가 `day`를 `"1"`이 아니라 **`"1일"`**로
반환하고 있었고 **아무 테스트도 이것을 보지 않았다.**

조용한 결함이 아니다. `buildPage`가 일차별 이미지 슬롯을 `itinerary_day_${day}`로
만드는데 업로드된 슬롯 이름은 `itinerary_day_1`이다. `day`가 `"1일"`이면
`itinerary_day_1일`을 찾게 되어 **일차별 사진이 페이지에 붙지 않는다.**

**원인은 산문과 프롬프트가 갈린 것이다.** SKILL.md 산문은 「`day`는 문자열로
저장한다(`"1"`)」로 규정했지만 **실행되는 `## 프롬프트` 펜스에는 그 규칙이 없었다.**

프롬프트에 규칙을 넣고 `checkDayNumbers`(0차 확정 위반)로 이중화했다. 값을 덮어쓰지
않은 이유: 고치면 **AI가 규칙을 어긴 사실이 사라진다.** 같은 어긋남이 `내용`·
`원문근거`에서 일어나도 알 수 없게 된다.

실증 — 이미지를 올린 채 `decompose → brochure → validate-brochure → page` 관통:

```
day 값       ["1","2","3","4"]
업로드 슬롯   [hero, itinerary_day_1..4]
페이지 슬롯   ["itinerary_day_1","itinerary_day_2","itinerary_day_3","itinerary_day_4"]
```

### ⑤-2 산문과 프롬프트가 갈리는 것을 막을 방법

# 8. spec 2.8 설계 — 상품 페이지의 「정해진 형식」을 없앤다 (2026-08-13 결정 · **착수는 데모 후**)

**아직 한 줄도 구현하지 않았다.** 이 절은 R6(「새 기능은 자리를 먼저 정한다」)에 따라
**자리와 근거만** 정해 둔 것이다. `spec.md`는 여전히 2.7이며, **착수하는 사람이
`spec.md`를 2.8로 올린 다음 코드를 고친다** — 규정만 2.8이고 코드가 2.7이면
그 사이에 구현하는 사람이 없는 규정을 믿는다.

## 8.1 먼저 알아야 하는 사실 — 지금 AI는 페이지 구성에 발언권이 없다

「템플릿 같다」는 진단은 정확하다. **페이지는 거의 전부 기계 조립물이다.**
AI 출력 계약(`EXPAND_SCHEMA`)이 전부 이것이다.

```
days[].text            일차 서술 확장
apply.제목·안내문구
```

섹션 9개·순서·테마·그 밖의 모든 값은 `buildPage`가 확정 데이터표에서 조립한다
(`lib/pipeline/page.ts` — `PAGE_SECTION_IDS` 9개 고정 배열 · `section(...)` 9회 호출).
**「AI가 자체적으로 생각해 만든다」를 하려면 AI의 출력 계약부터 넓혀야 한다** —
프롬프트를 고치는 일이 아니다.

### 그래서 「형식」이 실제로 어디에 박혀 있는가

| 곳 | 무엇이 고정인가 | 2.8에서 |
|---|---|---|
| `page.ts` `PAGE_SECTION_IDS` | id·타입·**개수 9**·순서 | **삭제** |
| `page.ts` `buildPage` | 9섹션 하드코딩 조립 | AI 구성 계획대로 조립 |
| `page.ts` `checkPage` | 「`ids.length !== 9`이면 위반」 | 어휘·커버리지·구조 최소 조건으로 |
| `consistency.ts` `SECTION_PAIRS` | 소개서 8 ↔ 페이지 9 **1:1 대응표** | **삭제** → `source` 커버리지 검사로 |
| `edit-contract.ts` `BASE_IDS` | 고정 9개가 불변 | **그 상품이 생성한 집합**이 불변 |
| `theme.ts` `STYLE_TO_THEME` | 여행스타일 → 테마 **1:1** | AI 선택 + 기계 검증·폴백 |

### 다행인 것 — 두 계층은 이미 구성에 무관하다

| 계층 | 왜 무관한가 |
|---|---|
| **렌더러** | `PageRenderer`가 `sections`를 순회하고 `order`로 정렬하며 `type → 컴포넌트` 맵으로 그린다. 개수·순서·반복·생략이 **이미 데이터가 정한다.** 「9섹션」은 렌더링 제약이 아니었다 |
| **2·3차 검증의 본체** | `collect()`가 **`source` 경로 문자열만** 조인 키로 쓴다(`consistency.ts` 주석). 섹션 id·타입에 의존하지 않는다 |

**즉 구성 자유와 4축 검증은 양립한다.** 매달려 있는 것은 `collect()` 위에 얹힌
`SECTION_PAIRS` 존재 검사뿐이고, 그것은 더 강한 검사로 갈아탈 수 있다(§8.4).

## 8.2 없애는 것과 남기는 것

**없앤다** — 고정 섹션 9개 · 고정 순서 · 1:1 대응표 · 「같은 타입은 한 번만」.
AI가 **어떤 블록을 · 몇 개 · 어떤 순서로 · 어떤 분위기로** 놓을지 정한다.

**남긴다 — 블록 어휘(렌더러가 아는 `type` 목록).** 여기가 이 설계에서 유일하게
타협하지 않은 경계이고, 근거를 분명히 적어 둔다.

> 어휘를 없애는 것은 **AI가 HTML·CSS를 직접 쓴다**는 뜻이다. 그 순간 다섯 개가
> 동시에 깨진다 — ① 375/768/1280 반응형 보증(§17.2) ② 대비 4.5:1 ③ 편집기의
> 섹션 단위 편집(§10) ④ XSS 안전 ⑤ **40초 예산** (페이지 확장이 지금 11.7초인데
> HTML 전문 생성은 출력 토큰이 한 자리 수 배로 늘어난다 — 2.7에서 분해가 35.3초로
> 4.7초만 남긴 것을 보면 여유가 없다). 이것이 절대원칙 5·§9.1의 근거다.

**그래서 표현력은 어휘를 넓혀서 늘린다.** 조합할 재료가 9종뿐이면 자유를 줘도
결과가 비슷하다. **새 블록 타입을 추가하는 것이 이 작업의 절반이다.**

| 기존 9종 | 추가 후보 |
|---|---|
| hero · summary · itinerary · accommodation · flight · meal · price · shop · apply | `gallery`(사진 묶음) · `highlight`(강조 문구) · `quote`(후기·인용) · `timeline`(일정 축) · `map`(위치 묶음) · `cta`(중간 유도) · `spotlight`(한 곳 집중 소개) · `two-column` |

각 타입마다 **렌더러 컴포넌트 + 길이 계약 + 편집기 폼**이 필요하다 —
AI가 어휘를 늘릴 수는 없다. 어휘를 늘리는 것은 사람의 코드 작업이다.

## 8.3 AI에게 무엇을 쓰게 하고 무엇을 쓰게 하지 않는가

**2.7의 자연어 초안에서 세 번 실패하고 배운 것을 그대로 적용한다**(§7.5 ③).
AI에게 이름·주소·금액을 다시 타이핑하게 하면 발산하고 본문 0자가 된다.

| 주체 | 무엇 |
|---|---|
| **AI** | `theme` · `blocks[{type, order, 재료참조}]` · **서술 필드만** (일차 서술·`apply` 문구·`highlight` 문구 등 `source: "generated"`인 것) |
| **기계** | 사실정보 값 치환 — 행사명·기간·가격·숙소명·상점명·항공편은 **확정 데이터표에서 그대로** 꽂는다 |

**얻는 것이 두 개다.** ① 출력 토큰이 거의 늘지 않는다(블록 배열 + 서술 몇 개) —
AI 호출 **1회 유지**, 40초 예산 유지. ② **사실정보가 AI를 거치지 않으므로 바뀔 수 없다** —
§16.1이 구조적으로 지켜지고, 구성이 자유로워져도 검증이 약해지지 않는다.

## 8.4 검증을 「섹션 대응」에서 「`source` 커버리지」로 옮긴다

여기가 구성 자유를 가능하게 하는 핵심 교체다.

| 축 | 2.7 | 2.8 |
|---|---|---|
| 2차 (페이지 사실정보) | `source` 조인 | **변경 없음.** 섹션 id에 의존하지 않는다 |
| 3차 (소개서 ↔ 페이지) | `SECTION_PAIRS` 8쌍 존재 + `source` 값 대조 | **대응표 삭제.** 「소개서의 `source` 경로 집합 ⊆ 페이지의 `source` 경로 집합」 + 같은 경로의 값 문자열 동일 + 일정 배열(일차 수·번호·내용) 대조 |
| 계약 검사 | 섹션 9개·순서 일치 | **어휘 준수** · **정보 커버리지** · `apply` 1개 존재 · `order` 1..n 연속 · 타입별 길이 계약 |

**커버리지 검사가 「자유 구성」이 「값 누락」이 되는 것을 막는다** —
확정 데이터표의 모든 사실정보가 페이지 어딘가에 있어야 한다(재료가 `해당 없음`인 것 제외).
어느 블록에 있든 상관없다. **구성 무관하면서 2.7의 대응표보다 강한 검사다.**

`apply` 블록을 필수로 남기는 이유: 신청 폼이 없으면 상품 페이지가 아니다(§13.1).

## 8.5 「없는 것」과 「미정」을 구분한다 (§8의 최초 동기)

구성이 자유로워지면 AI가 항공 블록을 안 만들 수 있다. 그러면 **왜 없는지**를
기계가 판정해야 한다 — 재료가 없어서인지, AI가 빠뜨렸는지.

| 판정 | 규칙 | 근거 |
|---|---|---|
| 재료 **없음** | 값이 `해당 없음` → 커버리지 대상에서 제외 (블록 없어도 통과) | 기획자가 폼에서 명시적으로 「미이용」을 체크한 경우뿐 |
| 재료 **미정** | 값이 `추후 추가 예정` → **커버리지 대상.** 어딘가에 흐리게 표시 | §6.1의 목적이 「빈칸을 기획자가 알아차리게」다 |
| 재료 **있음** | 커버리지 대상. **빠지면 계약 위반** | §16.1 — AI가 사실정보를 지우는 경로를 만들지 않는다 |

**`해당 없음`을 신호로 쓰는 근거는 spec에 이미 있다** — §6.1의 `가격.아동` 미운영
체크가 같은 구조다. 새 개념을 만들지 않고 선례를 넓힌다.

## 8.7 소개서는 바꾸지 않는다 (8섹션 고정 유지)

기획자의 결정이다. 소개서는 **AI 주관 없이 값만 채워 검증하는 문서**로 남는다 —

**그래서 두 산출물의 성격이 갈린다** — 소개서는 고정 형식의 검토표, 페이지는 자유

그 끈을 「형식 일치」가 아니라 「정보 일치」로 다시 묶는다.

## 9.1 왜 바꾸는가 — 기획자는 일정을 적지 않는다

기획자가 실제로 적는 것은 이런 글이다.

> 금융권에서 일하는 동기생 A, B는 혼자서 하기에는 부담되는 걷기 축제를 함께 가서
> 제주의 가을을 제대로 만끽하고 싶어한다. 회사에서의 스트레스는 제주의 맛집과
> 카페에서 날려버리고 재충전하는 시간을 기대하는 29세와 31세의 여성이다. 2곳의
> 숙소에서 1곳은 고가의 제주구옥에서, 다른 한곳은 마을 안에 있는 타운하우스에서
> 숙박을 하며 마을 속에서 머물고자 한다.

여기에 **일차별 일정은 없다.** 그런데 2.7의 필수 폼 그룹은 `일정 원문`(20~2000자 ·
**일차 구분 표기 필수**)을 요구한다. 즉 **기획자에게 결과물을 먼저 쓰라고 요구하고 있다.**
일정 짜기는 가장 노동집약적인 부분이고, §1의 「입력부터 배포까지 10분」에 정면으로 걸린다.

## 9.2 정한 것 — 필수 폼 그룹 6개의 구성을 바꾼다 (개수는 6 그대로)

| 폼 그룹 | 2.7 | 2.8 |
|---|---|---|
| **의도** | — (`기획메모`가 선택 9종 중 하나) | **필수 · 폼 최상단.** 페르소나·바라는 결·제약 |
| **일정** | **필수** · 일차 구분 표기 필수 | **선택.** 있으면 근거로 쓰고, 없으면 재료로 조합한다 |
| 행사정보 · 숙박 · 상점 · 가격 · 식사 | 필수 | 그대로 |

**일정 필드를 없애지 않는다.** 기획자가 이미 일정을 확정한 상품(전세버스·고정 코스)이
있고, 그때는 사람이 쓴 일정이 AI 배분보다 정확하다. **선택으로 내리는 것과 없애는 것은
다르다.**

## 9.3 `기획메모`를 승격한다 — 새 필드를 만들지 않는다

의도 필드에 들어올 글은 **페르소나**다 — 「29세와 31세의 여성」·「회사에서의 스트레스」.
**고객에게 보이면 안 되는 값이다.**

spec §6.1에 이미 그 성격의 필드가 있다: `기획메모` (여러 줄 · 최대 1000자 ·
**고객 미노출 · 채움 대상 아님**). 그리고 `memo-leak-check`가 **「기획메모에만 있는
숫자가 고객에게 보이는 서술 필드에 노출됐는지」** 를 검사한다 — 나이가 든 위 예문에
정확히 필요한 장치다.

**그래서 새 필드를 만들지 않고 `기획메모`를 필수로 올린다.** 새로 만들면 고객 미노출
규정·마스킹(§5.4)·유출 검사를 두 번 쓰게 되고, 두 벌이 갈리는 순간 한쪽이 새는 통로가 된다.

| 무엇 | 값 |
|---|---|
| 위치 | 폼 **최상단** (지금은 선택 항목들 사이) |
| 필수 | 예 — 최소 길이를 정해야 한다(제안: 30자) |
| 상한 | 1000자 → **2000자로 상향 검토.** 위 예문이 250자이므로 여유는 있지만, 「의도」가 필수가 되면 길게 쓰는 사람이 생긴다 |
| 고객 노출 | **없음. 그대로 유지** |
| 쓰이는 곳 | ① 일차 배분의 판단 근거 ② **§8의 테마·구성 판단 근거** ③ 서술의 어조 |

## 9.4 `장소[]` 배열을 신설한다 — 이것 없이는 성립하지 않는다

**관광지는 지금 `form_input`에 자기 자리가 없다.** 실증:

```
freeform-parse   「여행지 포인트」 블록을 장소 후보로 뽑는다   (freeform.ts:92 · 122)
trip-planning    후보 번호를 일차에 배분한다
draft-assemble   배분 결과를 «일정원문» 문장으로 조립한다      ← 관광지가 여기 녹아든다
```

즉 관광지는 **일정 텍스트 안에만** 존재한다. `숙박[]`·`상점[]`처럼 구조화된 자리가 없다.
**일정원문이 선택이 되면 관광지가 갈 곳이 사라진다.**

| 신설 | 필드 | 필수 |
|---|---|---|
| `장소[]` | `장소명`(1~80자) · `위치`(1~60자) · `구분`(select: 관광지/체험/코스/행사장) · `설명`(선택 500자) | **선택 배열** (0행 허용) |

`상점[]`에 합치지 않는 이유: `상점[i].구분`이 `제휴`/`추천` 2종이고 이것은 **제휴 관계**를
뜻한다(§13.3 이메일과 §9.3 상점 섹션이 그 값을 쓴다). 관광지에 제휴/추천은 의미가 없다.

## 9.5 `원문근거`를 재정의한다 — 여기가 실질 비용이다

0차 검증의 1단계는 **문자열 부분 검사**다.

```
axis0.ts:119   /** 1단계 — `원문근거`가 `일정원문`의 부분 문자열인가. **기계**. */
axis0.ts:135   `${d.day}일차의 원문근거가 일정원문에 없습니다. 발췌가 아니라 재작성입니다.`
```

**일정원문이 없으면 이 검사는 대조할 대상이 없다.** 그런데 근거 없는 일차 서술을
허용하면 절대원칙 7이 무너진다.

### 모드 분기를 만들지 않는다 — 근거 집합을 넓힌다

「사람이 쓴 일정」과 「AI가 짠 일정」을 두 스킬·두 프롬프트로 가르면 R2·R4를 어기고
(프롬프트는 `## 프롬프트` 펜스 하나다) 런타임 데이터에 따른 체인 분기가 필요해진다.
**대신 근거의 출처를 넓힌다.**

```
근거 집합 = 일정원문(있으면)  ∪  재료 목록(숙박[].숙소명 · 상점[].상점명 ·
                                 장소[].장소명 · 행사정보.행사명 · 여행지)
```

**§6.3 판정 3단계가 이미 그 형태다.** 2.7에서 구현한 「AI가 `핵심표현`을 신고하고
**기계가 근거를 대조해 판정**한다」가 그대로 쓰인다 — 대조 대상만 「일정원문의 부분
문자열」에서 「근거 집합」으로 넓어진다.

| 항목 | 2.7 | 2.8 |
|---|---|---|
| `원문근거` 부분 문자열 검사 | 항상 | **일정원문이 있을 때만** |
| `핵심표현` 신고 → 기계 대조 | 일정원문·확정 값 | **근거 집합 전체.** 없는 이름을 쓰면 실패 |
| 판정 주체 | 기계 | 기계 (변경 없음) |

**결과적으로 지금보다 강해진다.** 부분 문자열 검사는 「원문에서 베꼈는가」만 보는데,
근거 집합 대조는 **「그 장소가 폼에 실재하는가」** 를 본다. AI가 제주에 있을 법한
카페 이름을 지어내면 2.7에서는 원문에 그 문장이 있었으면 통과할 수 있었지만, 2.8에서는
재료 목록에 없으므로 실패한다.

| 3 | `itinerary-decomposition` **(ai 1회)** | 입력에 `기획메모`·`장소[]`가 추가되고, **일정원문이 없으면 재료로 배분한다.** `## 프롬프트` 펜스를 고쳐야 한다 → **해시 갱신 · 캐시 프리픽스 새로 잡힘** |
| 4 | `axis0-verification` | 1단계를 조건부로, 3단계 대조 대상을 근거 집합으로 |

⚠️ **스킬 이름이 「분해」인데 「조합」도 하게 된다.** R2(단일 기능)의 경계에 걸리는
지점이므로 착수할 때 판단한다 — 이름을 `itinerary-build`로 바꾸는 편이 정직할 수 있다.
쪼개지 않는 근거는 §9.5(하나의 프롬프트·하나의 근거 집합)이고, **AI 1회 예산이 그것을
강제한다.**

## 9.7 자연어 초안 라우트(#20)와의 관계

폼이 자연어 의도를 받으면 #20과 역할이 겹친다. 정리는 이렇다.

| 경로 | 하는 일 |
|---|---|
| **#20 (초안)** | 메모 한 덩어리 → 폼 **전체** 채움. `기획메모`·`장소[]`까지 채운다 |
| **본류 (제출 후)** | 폼의 `기획메모` + 재료로 **일정을 짠다** |

**두 경로가 같은 결과로 수렴한다** — 메모를 #20에 붙여넣는 것과 폼에 직접 쓰는 것이
같다. #20의 `trip-planning`은 「폼을 채우기 위한 배분」이고 본류는 「확정 데이터표를
만들기 위한 배분」이므로 역할이 중복이 아니라 **단계가 다르다**(사이에 사람의 확정이 있다).

## 9.8 보증하지 못하는 것 — 착수 전에 알아야 한다

| 무엇 | 판단 |

| 완화책 | `위치`를 자유 텍스트에서 **권역 select + 상세**로 쪼갠다. 지금은 AI가 「제주시 조천읍 …」 문자열에서 권역을 추측한다. 「마을 속에서 머문다」 같은 의도를 살리려면 권역이 명시적이어야 한다 |

| 필수 그룹 재편의 문서 파급 | `spec.md` §7.1·§7.2·§6.1·§6.3·§11.1 · `checklist.md`(필수 6개를 참조하는 항목 전부) · 관문 검사 400/422 경로 · §8.6 「필수 6개 전부 반영」 |

## 10.1 고친 결함 3건 (커밋 `bc4562c`)

### ① `brochure_ready`의 [입력 수정]이 빈 폼으로 떨어졌다

§15.1은 그 상태의 버튼으로 [입력 수정]을 규정하는데 §14.4 #17의 허용 상태는
`input_error`만이었다. **두 규정이 어긋난 자리로 UI가 빠졌다.**

**보이는 증상보다 나빴다.** 값이 안 채워지는 것에 그치지 않고, `productId`가 없으니
`resubmit`이 거짓이 되어 제출이 #17(교체)이 아니라 **#1(신규 등록)** 으로 갔다 —
원래 상품을 그대로 두고 **다른 상품이 하나 더 만들어진다.** 기획자에게는
「정보가 사라졌다」로 보인다.

허용 상태를 `brochure_ready`까지 넓혔다. 근거는 §8.3이다 — 「재시도가 소진되면
`input_error`가 아니라 `brochure_ready`로 두고 [다시 생성]·[입력 수정]을 제공한다」.
`/new`는 판정을 다시 쓰지 않고 `checkPrecondition`에 묻는다(목록을 하나로).

### ② 필수 입력 누락 시 페이지 최상단으로 튀었다

`stop()`이 항상 `scrollTo({ top: 0 })`이었다. 폼이 길어(필수 6그룹 + 선택 9)
최상단에서는 **어느 칸이 문제인지 화면에 없다** — 오류 문구는 그 칸 옆에 있다.
오류가 있는 첫 칸으로 이동하고 커서를 놓는다. 「첫」은 오류 객체의 키 순서가 아니라
**화면에서 가장 위**다(키 순서는 검증기가 만든 순서다).

### ③ 연결 실패가 「40초 타임아웃」으로 기록돼 원인을 숨겼다

`classify()`가 `/abort|timed? ?out/`에 걸리는 모든 오류를 `timeout`으로 잡았다.
DeepSeek에 연결이 안 되는 상태에서 SDK가 «Request timed out.»을 던지는데 실제 경과는
**10.6초**이고 모델은 호출조차 되지 않았다. **로그만 보면 「모델이 느리다」로 읽히는데
조치는 정반대다** — 이 문서를 쓰는 사람도 처음에 그렇게 읽었다.

경과 시간으로 가른다 — 예산의 80%도 쓰지 않고 끊겼으면 예산 초과가 아니다.
실패 6종을 늘리지 않고 `api_error`(§4.3 「5xx·네트워크·인증」)로 보낸다.
